# AI生成 基準書

## AI向け指示

- **作業前**: 依頼内容に応じた `004_Guideline/Japanese/*_Standards.md` と、該当する `004_Guideline/templates/*_Template.md` / `*_Template.html` を **Read ツールで読む**（プロジェクトルール `.cursor/rules/*.mdc` と併せて従う）。
- **AI モデル**: デフォルトは **Cursor Grok 4.5（High）**。詳細は `Guideline_Cursor.md`「4.2.1 AI モデルの選択」。
- **用語**: 用語の調査・改称・定義確認は、まず `003_Common/101_Requirement_Defination/Glossary_Reservation.md`（および関連 Glossary）を**頂点**に確認する。用語集に無い語を書類へ広げない。
- **コンテキスト**: 関連文書は **`@` で明示**する。参考にすべき既存成果物があるフォルダも指定する。未指定で基準書が分からないときはユーザーに確認する。
- **矛盾**: プロンプトと各基準書が食い違う場合は **基準書を優先**し、差分はユーザーに確認する。
- **疑問**: 実行前に、全ての不明点をなくすため、一問一答形式でユーザーに質問を行う。
- **作業用 Python**: 一括処理・調査・変換などの作業用 `.py` と、その実行でできた一時ファイルは、生成物と同じフォルダに置かず **`007_Scripts/<用途>/`** に集約する（後述「作業用 Python の配置」）。


## 目的

本基準書は、AIでファイル生成を行う際のルールを定める。
高品質な設計書を効率よく作成することを目的とする。


## 文書作成の基本ルール

- AIの使用は、原則としてCursor内で行うこと。
- **AI モデルの選択**：選定・利用料確認・他モデル試用の会社方針は `004_Guideline/Japanese/Guideline_Cursor.md` の「4.2.1 AI モデルの選択」に従う。
- AIに指示を出す場合は、①基準書、テンプレート②参照ドキュメント③既存成果物を指定すること。
    - 関連する文書
        - 基準書: `004_Guideline/Japanese/` 配下の基準書（`*_Standards.md` 等）
        - 参照ドキュメント: 設計書などの該当するドキュメントを指定する
        - 既存成果物: 既に生成したファイルがある場合、参考にすると同じように生成してくれます。
    - プロジェクトルール（`.cursor/rules/*.mdc`）はワークスペース設定により付与されることがあるが、**設計書本文や基準書は `@` で明示**した方が確実である。
    - 引用方法
        - `@`を入力すると、フォルダ・ファイルの選択肢が出ますので、その中から選択する。
        - ファイルツリーで、フォルダ名やファイル名を右クリックした時に出てくるメニュー`Add File to Cursor Chat`より指定する
        - `@ファイル名` だけでなく `@フォルダ名` も有効とCursorのマニュアルにはあるが、全てのファイルが参照されない場合がある。
    - 文書のフォーマットは、`004_Guideline/templates/` 配下の `*_Template.md` / `*_Template.html` を指定すること。

## 文書修正の基本ルール

- 書類を修正する際は、まずAskモードで認識が正しいか確認してから、Agentモードで更新すること
- **用語の確認**は、対象書類を確認する前に **用語集**を確認する（定義の有無・正式名称・英語／ベトナム語・関連 No）。修正が必要の場合、用語集を更新してから、用語集以外の書類へ反映する。

## 文書ファイルのファイル名、形式

- 生成する設計書は、原則として、テキスト形式（Markdown）とするが、Drawioなど基準書で指定された形式に合わせる。
- 基準書で指定されたフォルダに保存する。
- フォルダ名・ファイル名は、命名規則に従う。


## 作業用 Python の配置

AI が文書生成・データ加工・調査のために一時的または再利用可能な Python を作成する場合の置き場所を定める。設計書やサンプルデータのフォルダに `.py` や作業用一時ファイルを散在させない。

| 項目     | 規則                                                                                                          |
| ------ | ----------------------------------------------------------------------------------------------------------- |
| 保存先    | リポジトリルート直下の **`007_Scripts/<用途>/`**（用途別サブフォルダ）。例: サンプルデータ加工なら `007_Scripts/205_Sample_Data/`                |
| 対象     | 一括変換・CSV/HTML/HAR 解析・プローブ・パッチ適用など、**作業・検証用**の `.py`                                                         |
| 一時ファイル | 中間 JSON・調査ログ（`*_out.txt` 等）・抽出キャッシュなど、**実行時に作成した一時／中間ファイルも同じサブフォルダ**に置く（成果物フォルダに残さない）                       |
| 禁止     | 生成した設計書・サンプルデータ・モックアップなど **成果物と同じフォルダ** への `.py`／一時ファイルの配置                                                  |
| 対象外    | `004_Guideline/templates/` に置くテンプレート本体（例: `Screen_Layout_Template.py`。未配置でもパス規約はテンプレート側の基準書に従う）             |
| 最終成果物  | 納品・レビュー用の最終出力のみ成果物フォルダへ書く（例: サンプル CSV は `003_Common/205_Sample_Data/*.csv`）。スクリプトと一時ファイルは `007_Scripts/` 側  |
| パス参照   | `WORK = Path(__file__).resolve().parent`（スクリプトのあるサブフォルダ）、`REPO = WORK.parents[1]`（リポジトリルート）。絶対パスのハードコードは避ける |

- 新規作成時は必ず `007_Scripts/<用途>/` に置く。既存の散在ファイルを見つけた場合は、同配下へ移しパスを直す。
- 用途サブフォルダ名は、対応する成果物フォルダ名に揃えると分かりやすい（例: `003_Common/205_Sample_Data`）。
- 用途が分かるファイル名にする（例: `build_sample_from_old_api.py`）。一時調査用は先頭に `_` を付けてもよい。


## 整合性のチェックの基本ルール

- AIが文書を生成した後や、人間が文書を作成した後は、AIにチェックしてもらうこと
    - 文章、内容が正しいか、漏れがないか
- AIにチェック方法: 設計書を元にAIにQA集を作ってもらい、人間がチェックする
    - Answerが間違っている場合、設計書が間違っていると考えられる
    - 生成したQAは、ヘルプセンターの元ネタとする
    - **ヘルプを作成することまでが設計書作成フェーズ**とする（正しいヘルプをAIが作成するまで設計書を修正し続ける）
- 設計書の整合性チェックは、関連する設計書を全て指定するのを忘れないこと。
- 上司やお客様にレビューする前に、必ず設計者が確認すること。


## 運用について

- 新しいAI利用方法を見つけた場合、または問題が発生した場合、必ず上司に報告すること。
- 仕様の理解に迷った場合は、必ず上司に確認すること（AIの回答を信用しない）

## AIでシステム開発を行う上でのコツ

AIで設計・実装・文書生成を進める際の実践的なノウハウをまとめる。
前提として **AIは常に手を抜こうとする・推測で捏造する** ものとして扱い、人間が枠組みと検証を用意する。

### 進め方（計画とQA）

- **必ず計画を立てさせてレビューする（Plan Mode）**: いきなり実行させず、まず計画を立てさせ、タスクの加筆・修正をしてから実行する。
- **スロットフィリング（穴埋め）でQAをやり切る**: 計画を立てる前に、**質問が無くなるまでQA**を行う。**一問一答形式**で進めると、前の回答を加味した次の質問が出るため精度が上がる。
- **QAはプロンプトや計画に入れず、人間が独自に実施する**: プロンプトに「不明点は質問してください」と書いても、AIは1～2個質問しただけで次の作業を始める。**不明点をなくすことではなく質問すること自体が目的化**するため、QAはAI任せにせず人間主導で行う。
- **会話のLogを必ず取る**: 特にQAは詳細にログを残す。「何を聞かれ・どう答えたか」だけでなく、**最終的に確定した仕様（決定事項）**まで残し、QA集・ヘルプ作成（本書「整合性のチェック」）の元ネタとする。
- **タスクは小さく区切る**: 1回のプロンプトで大きな仕事をさせない。**1タスク＝1検証単位**に分割すると、ズレたときに巻き戻しやすい。計画も人間がレビューできる粒度に分解させる。

### グラウンディング（捏造させない）

- **正本を必ず与える**: AIは情報がないと、それらしく捏造（ハルシネーション）する。判断の根拠となる**正本（基準書・既存設計書・コード）を必ず添付**し、**「ソースに無いことは書かない／不明は『不明』と返す」**と明示する。
- **今必要なファイルだけを渡す**: 「フォルダ丸渡し」より、必要なファイルだけを `@` で渡す方がノイズが減り精度が上がる。
- **コンテキストの劣化に注意**: 会話が長くなるほど最初の指示や前提を忘れ精度が落ちる。区切りで**新しいチャットに切り替える**、または**現状の要約を作らせてから引き継ぐ**。

### プロンプトの組み立て

- **出力フォーマットを固定する（ガードレール）**: 期待する出力形式（テンプレート・項目・順序）を先に提示する。
- **肯定形で書く**: 禁止事項は「〜するな」より「〜してください」と肯定形の方が効きやすい。
- **Few-Shot（少数の例示）**: 過去に褒められたお手本（成功体験）を見せてから回答させる。**「良い例」だけでなく「悪い例＋なぜダメか」**も併記するとさらに効く。

### 検証と失敗対応

- **最終確認は必ず人間**: AIの回答を信用しない（本書「運用について」と同旨）。AIに**別観点で自己レビュー**させると見落としを拾えることがある。
- **失敗ループから抜ける**: 同じ誤りを繰り返す・修正がループする場合は、会話を続けず**新しいセッションでやり直す**。直らないときはプロンプトを足すより**前提・正本の不足を疑う**。
- **戻せる状態を保つ**: コード変更は **git で差分管理**し、大きな変更前にコミットしていつでも戻せるようにする。

### AIの構成・使い分け

- **インテント・ルーティング**: AIに処理の分岐をしてもらう。基本は**「司令塔（ルーター）」となるAI**と**「各タスクの専門家」のAI**に分ける。
- **モデルを使い分ける**: 重い設計＝高性能モデル、定型作業＝軽量モデルのように、タスクに応じて使い分ける。
- **APIはステートレス**: OpenAIなどのAPIは過去の会話を一切覚えない。会話の続きとして扱うには、**直近数回のやり取りを一緒に送り直す**必要がある。

### 機密情報の取り扱い

- **社外秘・個人情報を外部API（OpenAI等）に送らない**。どのモデル・環境なら何を渡してよいか、線引きを守る。

### モデル別の注意（Gemini）

- 指示や情報源が無いと弱い。
- 指示文はテキストが望ましいが、Google Workspace はテキストとの相性が悪い。
- どのAIモデルでもフォルダ丸渡しは良くないが、Gemini は特に苦手。


## 変更完了時の報告（必須）

アプリコード（Laravel / Inertia React）・ルート・言語ファイル・設計書などを **作成・変更・削除** した作業では、ユーザーへの回答の **末尾** に必ず次の2ブロックを載せる。省略しない。

### 1. デプロイ用・修正ファイル一覧

- リポジトリ（例: `add_pet`）または設計書ルート（`750_AddPet`）からの相対パスで列挙する。
- 追加・変更・削除が分かるよう `[追加]` `[変更]` `[削除]` を付ける。
- 設計書のみの変更は「文書のみ」として分けてよい。
- git が使える場合は `git status` で確認してから記載する。

### 2. マイグレーション

| 状況                                                         | 記載内容                                      |
| ------------------------------------------------------------ | --------------------------------------------- |
| DB・スキーマ・`database/migrations/*.php` に変更なし         | **`マイグレーション: 不要`** と明記           |
| Laravel migration 追加・変更あり                             | **適用コマンド**と migration ファイル名を記載 |

**AddPet（Laravel）の適用（AWS 上の対象環境）**

- 開発／検証: `php artisan migrate`（必要なら `--pretend` で確認後に実行）
- 本番: チームのデプロイ手順に従い、承認後に migrate を実行する（勝手に本番へ流さない）
- 追加した migration 名（例: `2026_07_24_000001_create_pets_table`）を1行で書く

**記載例（DB変更あり）**

```markdown
## デプロイ用・修正ファイル一覧
- database/migrations/2026_07_24_000001_create_pets_table.php [追加]
- app/Models/Pet.php [追加]

## マイグレーション
php artisan migrate
（2026_07_24_000001_create_pets_table: pets テーブル追加）
```

**記載例（DB変更なし）**

```markdown
## マイグレーション
不要
```

サブシステム／アプリ固有のデプロイ規約（`.cursor/rules` 等）がある場合はそちらを優先する。
