# 日次作業履歴 基準書

## AI向け要約

- **正本**: 本書。旧名称 `Daily_Update_History_Standards.md` はポインタのみ（内容は本書）。
- **目的**: その日の作業内容を **抜け漏れなく** 一覧化する。時系列の作業日誌ではない。
- **抽出条件（両輪）**: (1) リポジトリ内ドキュメントの **更新履歴行**（対象日・対象更新者） (2) **当該チャットの内容**（履歴行だけで判断しない）。
- **保存先**: `008_Work_history/Japanese/` と `008_Work_history/Vietnamese/`（言語別ファイル。1ファイル内の日越併記はしない）。
- **個人ファイル**: `Work_History_YYYYMMDD_<更新者名>.md`
- **全員マージ**: `Work_History_YYYYMMDD.md`（**対象**コードでマージ。個人作成のたびに再生成）
- **更新者名**: 作業者名（明示がなければ確認）。
- トリガー文言: **「作業履歴を作成して」**（「日報を作成して」も同義）。
- 着手前に本書を Read すること。旧形式見本（`008_Update_history/`）は参考のみ。

## 目的

- 1日分の作業内容（ドキュメントや決定事項）を記録し、後から内容を追えるようにまとめる。
- 作業内容の**抜け漏れ防止**を最優先とする（Chat内容の再現や時系列に作業を並べることはしない）。
- レビュー・引き継ぎ・翌日の作業開始時に、何を作成したか、何が変わったかを短時間で把握できるようにする。
- 全員分は **対象コード横串** のマージファイルで一覧できるようにする。

## 適用範囲

| 含める | 含めない（原則） |
| ------ | ---------------- |
| 対象日・対象更新者の更新履歴行があるファイル | 他更新者のみの更新（必要なら個人ファイル末尾「参考」で短く） |
| 要件定義・画面設計・DB・Code Master・スクリプト・PPTX 等の成果物 | チャットだけの検討でファイル未変更のもの |
| 履歴テーブルが無いが、対象日に作成・更新した成果物（例: PPTX・Mock） | 一時ファイル・調査ログ |
| 更新履歴行が無くても、チャット上で作成・更新したことが分かる成果物 | |

対象日・更新者が指示に無いときは、**作成前に確認する**（推定で進めない）。

## 1. 「作業履歴を作成して」時の必須手順

追加の詳細指示が無くても、次をすべて実行する。

1. **対象日**（`YYYY/MM/DD`）と **更新者名** を確定する。無ければ確認して停止する。
2. 既存の個人ファイルがあれば Read し、**上書き削除せず和集合マージ**する。
   - JP: `008_Work_history/Japanese/Work_History_YYYYMMDD_<更新者>.md`
   - VN: `008_Work_history/Vietnamese/Work_History_YYYYMMDD_<更新者>.md`
3. **更新履歴行**をリポジトリ全体から検索し、対象日・対象更新者の行を **全て** 拾う（打ち切り禁止）。
   - 日付表記ゆれ: `2026/08/03` / `2026-08-03` 等
   - 更新者の大文字小文字・誤記ゆれも拾う
4. **当該チャット**から、作成・修正した成果物と「何が変わったか」を抽出する（必須）。
   - 履歴行があるもの → 概要の肉付けに使う
   - 履歴行が無いが成果物が変わったもの → **必ず含める**
   - チャットだけの検討でファイル未変更 → 含めない
5. 履歴・チャット・既存個人ファイルを和集合化し、**対象 × 作業カテゴリ** 単位で行にする。
6. 作業概要が薄い行（「更新した」のみ等）は、履歴原文・チャットを再読して肉付けする。
7. **JP 個人ファイルと VN 個人ファイルの両方**を作成／更新する（行の `#` と対象を対応させる）。
8. 続けて、両言語フォルダで **全員マージ** `Work_History_YYYYMMDD.md` を再生成する（後述）。
9. 個人ファイル末尾の対象ファイル一覧と、作業一覧行を突合する。

### 複数チャット

- 各チャットでは最小プロンプト（本書メンション＋「作業履歴を作成して」）でよい。
- 2本目以降は既存個人ファイルへマージし、全員マージを再生成する。
- 完成条件: その日使った全チャットで一度は本手順を実行済みであること。

### 検索範囲の目安（漏れやすい場所）

- `10000_Reservation_System/**/101_Requirement_Definition/`
- `10000_Reservation_System/**/102_Screen_Design/`
- `20000_Hospital_System/`（該当作業があれば）
- `003_Common/104_Database_Design/`
- `004_Guideline/`
- その他、当日触ったフォルダ・チャットで言及されたパス
- 第1検索は **リポジトリ全体**。目安フォルダだけに限定して打ち切らない。

## 2. ファイル名・保存先

| 項目 | 規則 |
| ---- | ---- |
| ルート | `008_Work_history/`（リポジトリルート直下） |
| 言語フォルダ | `Japanese/` / `Vietnamese/` |
| 個人 | `Work_History_YYYYMMDD_<更新者名>.md` |
| 全員マージ | `Work_History_YYYYMMDD.md` |
| 例（個人） | `008_Work_history/Japanese/Work_History_20260807_Danh.md` |
| 例（全員） | `008_Work_history/Japanese/Work_History_20260807.md` |
| パス | 英数字・アンダースコアのみ。日本語パス禁止 |
| レガシー | `008_Update_history/` と旧ファイル名は残置。新規作成には使わない |

同一日・同一更新者の個人ファイルは原則1つ（言語ごと）。追記・再作成時は抜け漏れ再突合を行う。

## 3. 個人ファイルの文書構成（順序固定）

使わない節は設けない（空節を残さない）。テーマ別の長文節（旧 `## 1. …`）は **作らない**。

1. **タイトル**: `作業履歴 — YYYY/MM/DD（更新者名）`
2. **根拠**: 更新履歴行と当該チャットの両方から抽出した旨（1〜2文。その言語のみ）
3. **作業一覧**: 表（下記）
4. **補足**: 必要なときだけ。判断根拠・残課題など。無ければ節自体なし
5. **対象ファイル一覧（チェック用）**: フォルダ種別ごとに全ファイルを相対パスリンクで列挙

### 3.1 作業一覧表

| # | 対象 | 作業カテゴリ | 作業概要 |
| - | ---- | ------------ | -------- |

#### 対象列

その行の主対象を書く。

| 作業の性質 | 対象に書くもの | 例 |
| ---------- | -------------- | -- |
| 要件定義 | 要件番号 | `1008` |
| 機能設計 | 機能番号 | プロジェクトの体系に従う |
| 画面 | 画面番号 | `13000` / `1A200` |
| DB | テーブル名 | `reservations` |
| メッセージ | メッセージIDまたは定義書名 | `1A200-V03` |
| ガイドライン | 文書名（短縮可） | `Daily_Work_History_Standards` |
| 見積 | 見積ファイル名（短縮可） | `Estimate_FE_BE_10000_Danh` |
| モック | 画面番号 | `1A110` |
| 横断 | 範囲 | `12000–19000` |

同一対象でカテゴリが違う作業は行を分けてよい。

#### 作業カテゴリ（固定語彙）

次のいずれか。増やす場合は先に本書の語彙表を更新する。

| JP | VN（対応） |
| -- | ---------- |
| 要件定義 | Định nghĩa yêu cầu |
| 機能設計 | Thiết kế chức năng |
| 画面設計 | Thiết kế màn hình |
| DB設計 | Thiết kế DB |
| メッセージ定義 | Định nghĩa message |
| モック | Mock |
| ガイドライン | Guideline |
| 工数見積 | Estimate |
| Code Master | Code Master |
| その他 | Khác |

「その他」を使う場合は、概要の先頭で種別を明示する。

#### 作業概要

- 「更新した」「レビューした」だけは禁止。
- **何がどう変わったか**を1〜2文（目安 40〜120字）。
- 各設計書の更新履歴行の要点と、チャットで決まった方針を反映する。
- 記号の羅列だけで終わらせない（必要なら括弧で併記）。

### 3.2 補足（表外）

次だけを、作業一覧の `#` を参照して短く書いてよい。不要なら節を作らない。

- 判断根拠（Req／打合せ日など）
- 複数チャットをマージした旨
- 例外・残課題

### 3.3 対象ファイル一覧

- バッククォートのファイル名だけにしない。
- 個人ファイルからの **相対パス** で Markdown リンクにする。
- JP 成果物と VN 成果物があるときは、一覧内で対になるよう並べる。
- 新規作成は（新規）を付してよい。

```md
- [1A200_PetRegister_jp.md](../../10000_Reservation_System/Janpanese/102_Screen_Design/1A200_PetRegister/1A200_PetRegister_jp.md)
- [1A200_PetRegister_vn.md](../../10000_Reservation_System/Vietnamese/102_Screen_Design/1A200_PetRegister/1A200_PetRegister_vn.md)
```

## 4. 全員マージファイル（`Work_History_YYYYMMDD.md`）

### 目的

その日の全員の作業を、**対象コード横串**で一覧する。

### 作成タイミング

個人ファイルを作成または更新したら、**同じ応答内で**同日の全員マージを必ず再生成する（JPフォルダ・VNフォルダそれぞれ）。  
個人が1人しかいない日も作成する。

### 入力

同一言語フォルダ内の `Work_History_YYYYMMDD_*.md`。  
ただし `Work_History_YYYYMMDD.md` 自身は除外する。

### マージ規則

1. 各個人ファイルの作業一覧行を集める。
2. **対象** の値でグループ化する（前後空白除去。`–` と `-` の同一視など迷わない範囲のみ正規化。迷ったら分けたまま）。
3. 表は **対象でソート**（番号・コード系を先に、その他は文字順）。
4. 同一対象に複数行ある場合、**行は潰さず残す**。同一対象内の並べ順は 更新者名 → 作業カテゴリ。
5. 個人側の「補足」は原則マージ表に混ぜない（日次横断でどうしても必要なときだけ末尾に短く）。
6. 末尾に **対象ファイル一覧（全員・パス重複除去）** を置く。
7. フォルダに存在する個人ファイルだけを対象とする（未提出者は含めない。後から個人が追加されたら再生成で取り込まれる）。
8. 自分の更新で、他更新者の個人ファイルに由来する行を消さない。

### マージ表の列

| # | 対象 | 作業カテゴリ | 作業概要 | 更新者 |
| - | ---- | ------------ | -------- | ------ |

`#` はマージファイル内の通し番号（個人ファイルの `#` と一致させなくてよい）。

### マージファイルの構成

1. タイトル: `作業履歴 — YYYY/MM/DD（全員）`
2. 根拠: 同日の個人作業履歴（更新者名を列挙）を対象コードでマージした旨
3. 作業一覧（マージ表）
4. 対象ファイル一覧（全員・重複除去）
5. （任意）補足

## 5. 抜け漏れ防止・記載ルール

- 抽出は **更新履歴行** と **当該チャット** の両輪。履歴行だけで完了としない。
- テーマを先に決めてからファイルを探さない。先に和集合の行を揃えてから表にする。
- 代表例だけ挙げて「同様の更新あり」で省略しない。
- 同一対象で JP／VN／Overview／Design／DB が分かれて更新されていても、**対象ファイル一覧には全て列挙**する。
- 対象更新者の行が VN 設計書に無い場合は、一覧に載せたうえで「VN に当該更新者の履歴行なし」と注記してよい（推測で未更新と断定しない）。
- 作業の時刻順・会話順で並べない。
- 「何時ごろ依頼したか」などの経過説明は書かない（必要な経緯は補足1〜2文まで）。
- JP 個人と VN 個人で、行の対象対応を崩さない。
- ベトナム語の IT 用語は [`Translation_Standards.md`](./Translation_Standards.md) に従う（VN ファイル作成時）。

```

```
